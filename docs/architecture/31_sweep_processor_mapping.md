# 31 · Worker sweep and processor mapping (L19, L20)

Every one of the 22 sweeps in `apps/worker/run.py::sweep_table` and the 5 worker processors, mapped one by one. Rules: time-based → DBOS scheduled workflow or durable timer; event-based → Kafka (Redpanda) consumer fed by the Postgres outbox. Every consumer dedupes on `processed_events(consumer, event_id)` plus the idempotency key below. Each move ships with a parity test (old sweep output = new output on the same fixture) and the old sweep stays behind `WORKER_PAUSED_SWEEPS` until the parity test passes in CI. Placement: all workflows run on the **Ubuntu** workers when up; the droplet runs a minimal DBOS executor for the customer-facing ones (job offers, delivery SLA, notifications, webhooks, Interac matching) so Ubuntu-off does not stop operations (see 28). DBOS queues dedupe across both executors because state lives in Postgres.
