D-U-N-S 243332549 already issued; Play organisation account created in Phase 0); the Shopify app installed as an unlisted custom app on the pilot store (L30), with the public-listing path written down.

6. Hybrid deployment (L28) running, admin only over WireGuard, failover drills passed.
7. **No agentic mode.** Every existing AI feature is switched off behind a flag, and nothing new with an LLM is built. Phase 1 starts from a clean, deterministic system.

Facts (local 55632, read-only, 29 Oct): 129 data tables + `alembic_version`, all in `public`; 0 tables without a PK; 32 tables with no FK in or out; 51 free-string `status` columns; table-name prefixes are mixed (`crm_` 16, `merchant_` 12, `driver_` 11, `notification_` 8, `dispatch_` 6 … and singletons like `stops`, `leads`, `drivers` beside `driver_*`, `bookings` beside `booking_*`).

1. **Domain schemas** (D-P0-4): `identity`, `crm`, `merchant`, `customer`, `ordering`, `dispatch`, `driver`, `billing`, `pricing`, `notify`, `shopify`, `content`, `audit`, `platform`. Tables move with `ALTER TABLE … SET SCHEMA` in one Alembic revision; the API sets `search_path` so ORM names keep working during the move, then models gain `__table_args__ = {"schema": …}`.
2. **Naming rule:** plural snake_case nouns, no domain prefix inside a domain schema (`dispatch.job_offers`), FK = `<singular>_id`, timestamps `created_at`/`updated_at` timestamptz, money as integer cents with `_cents`, every enum a Postgres enum or a CHECK listing values from `domain/states.py`.
3. **Keys and relations:** every isolated table gets an FK or a written reason (log/audit tables such as `admin_audit_logs`, `domain_events` keep none by design). `leads` vs `crm_leads` and `customers` vs `porterchain_users` are reviewed for duplication. FK indexes on every FK column.
4. **Merges:** `crm_invoices` → view over `billing.invoices`; `crm_quotations` → view over `ordering.quotes` (A19).
5. **Drops** after `git grep` + row-count check + 30-day archive to Garage: `clerk_webhook_events` (after R8), `identity_migration_*` (after R6/R8 close), `legacy_external_refs`, `fk_orphan_quarantine` (after orphan report is empty), `route_center_templates` (resolve A25 first), `stripe_payouts` only if no retail payout use (U60-5).
6. **Alembic:** rehearse on a copy of 55632, then squash to one baseline `p0_0001_baseline` matching the live schema dump; linear history after; CI runs `alembic upgrade head` + `alembic check` on an empty DB and on a restored backup.
7. **Live cut-over:** schema changes reach live only in week 10 with the hybrid deploy, after a full restore rehearsal; never against 5432 from a dev box.

## 13. L32 decisions (Ravi, 29 Oct 2026)

D-P0-1..7 as in §12. Details for routing and Shopify pricing:

### 13.1 Routing engines (D-P0-6)

| Job                                             | Engine                                                                                               | Why                                                                                                                                                                                                                                                                               |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Route plans (turn-by-turn geometry, ETAs, legs) | **Valhalla** (self-hosted)                                                                           | `truck` costing: height, width, length, weight, axle load, hazmat, and `exclude_polygons` for restrictions; time-dependent costing                                                                                                                                                |
| Multi-stop optimisation                         | **VROOM** (self-hosted, BSD-2, free)                                                                 | Solves VRP with time windows (`time_windows`), capacity (`capacity`/`delivery`/`pickup`, multi-dimensional: kg, m³, cooler slots), driver shifts (`vehicles[].time_window`, `breaks`), skills (cooler, liftgate), pickup-and-delivery pairs (`shipments`), priority and max tasks |
| Distance/time matrices                          | **Valhalla `sources_to_targets`** by default; **OSRM `table`** only if it wins the benchmark (§13.2) | OSRM is faster for large matrices but has no truck costing; used only for car/van matrices                                                                                                                                                                                        |

VROOM never calls a router itself in production: the routing service builds the matrix (Valhalla or OSRM), passes it as `matrices` to VROOM, then asks Valhalla for the final geometry of each VROOM route. One matrix source per plan, recorded on the plan.

### 13.2 Benchmark (Phase 0 week 7, decides OSRM)

- **Data:** real orders from the Toronto + 150 km area — the last 90 days of `orders`/`stops` copied from the local 55632 DB (anonymised: coordinates rounded to 4 decimals, no names), plus 20 saved day plans. If there are fewer than 500 real stops, top up with synthetic stops sampled from real postal-code density and label the result.
- **Cases:** matrix 25×25, 50×50, 100×100, 200×200; 50-stop VROOM plans with windows + capacity + shifts; one truck plan with low-bridge and weight restrictions.
- **Measures:** p50/p95 matrix latency (10 runs, warm), RAM and CPU on Ubuntu and on Oracle A1 (arm64), duration accuracy against actual driver GPS durations for completed stops (MAPE), distance delta, and the plan cost (VROOM total duration) on each matrix.
- **OSRM wins only if** all three hold: p95 ≥ 2× faster at 100×100 and above, MAPE no worse than Valhalla + 2 points, and plan cost within 1 %. Otherwise OSRM is removed (container, data build, code, `osrm` refs = 0).
- **Output:** `docs/architecture/benchmarks/routing_2026.md` plus the raw CSV; the decision is recorded as L-number.

### 13.3 Service design

- `dispatch_engine/routing/` is the only code that talks to engines. Interface: `matrix(points, profile)`, `route(stops, profile, vehicle)`, `optimise(jobs, vehicles, options) -> Plan`, `health()`.
- Adapters: `valhalla_ubuntu` (full Ontario), `valhalla_oracle` (GTA + 150 km), `osrm_*` (only if kept), `vroom_local` (VROOM binary/`vroom-express` on Ubuntu, a second copy on Oracle), `haversine_estimate` (straight line × 1.35 at 40 km/h urban / 70 km/h highway, every value flagged `estimated=true`).
- **Fallback order:** Ubuntu → Oracle (3 s timeout each, circuit breaker opens after 3 failures for 60 s) → haversine × 1.35. VROOM falls back to Oracle VROOM, then to the current `vrp.py` greedy heuristic on the haversine matrix (flagged). Plans built on estimates can be saved but not sent to drivers without a dispatcher's confirm.
- Every plan stores: engine used, matrix source, fallback level, VROOM summary (cost, unassigned + reason), input hash; the same input gives the same plan (deterministic).
- Events: `pc.dispatch.v1` `plan.optimised`, `plan.published`, `route.fallback_used`.
- Budgets: 50 stops < 5 s, 200 stops < 30 s end to end (matrix + VROOM + geometry).

### 13.4 Ops page integration (Today, Plan, Live, Exceptions, Fleet; §9)

- **Plan:** Optimise button → VROOM; diff preview (moved stops, km, minutes, cost, margin band); unassigned list with VROOM's reason (window, capacity, shift, skill); lock a stop or driver before re-optimising; undo; banner "Estimated routes (fallback)" when the fallback level > 0.
- **Live:** Valhalla geometry on MapLibre; ETA re-computed from live GPS every 2 min with Valhalla `route`; at-risk sorting.
- **Today:** routing health tile (Ubuntu / Oracle / estimate), share of plans built on estimates today.
- **Exceptions:** `route.fallback_used` and unassigned-by-optimiser create typed exceptions with an owner and SLA timer.
- **Fleet:** vehicle profile (dimensions, weight, axle, cooler slots) and shift editor feed VROOM `vehicles` and Valhalla truck costing.

### 13.5 Shopify pricing and billing (decided)

- **No Shopify Billing.** PorterChain bills each merchant its contract price per job through the Interac invoice (merchants are Interac-only).
- **The merchant sets what its customers pay** for shipping. The app returns carrier-calculated rates at checkout from `contract price` + the merchant's rule: markup % or $, discount % or $, flat price, free over $X, per-zone override. Stored per merchant in `shopify.rate_rules`; the rate shown and the PorterChain price are both stored on the order so the margin is auditable. Rate response uses a stable `service_code`, CAD subunits, and returns an empty list for out-of-area addresses.
- **Verified 29 Oct 2026 (shopify.dev, help.shopify.com, Shopify dev forum), conflicts flagged:**
  1. **Carrier-calculated shipping needs the store's plan.** Creating a CarrierService fails unless the store is on Advanced or higher, or on the Shopify (Grow) plan with yearly billing or the paid CCS add-on, or is a non-Basic dev store. **Basic stores cannot use it at all.** If the plan changes, the carrier service is deactivated. Fallback for those merchants: the app writes the merchant's flat/zone rates into Shopify shipping profiles (Delivery Profile API) and PorterChain still bills its contract price by Interac.
  2. **Custom distribution = one store** (or several stores in one Plus organisation, or dev stores). It fits the pilot (L30). It does not scale to many merchants: that needs a public (listed or unlisted) app, which must pass App Review.
  3. **Public apps, listed or unlisted, must use Shopify App Pricing or the Billing API for all app charges.** Since March 2026, Shopify no longer grants limited-visibility exemptions. Our model charges nothing for the app (free plan) and bills the delivery service off-platform. That is a common pattern for logistics apps, but whether App Review treats delivery fees as "app charges" **is not confirmed. Ask Shopify Partner Support before the public-app work (Phase 2, doc 51).** Custom apps cannot use the Billing API at all, so the pilot has no conflict.
  4. The rate callback has no retry, and a timeout or error shows backup rates. The rate endpoint runs on the droplet (not Ubuntu), answers from cached contract prices + rules without calling routing, and the merchant must set backup rates.
